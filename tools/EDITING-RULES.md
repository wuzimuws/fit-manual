## 一、五个工具脚本

```bash
cd ~/Desktop/fit-manual
bash  tools/check.sh          # 1. 体检（11 项）
python3 tools/build_book.py   # 2. 重建 全书-通读版.md
python3 tools/build_web.py    # 3. 重建 web/index.html
python3 tools/find_dupes.py   # 4. 查重复（加条/搬条之后跑）
python3 tools/verify_refs.py  # 5. 列出所有条号引用 → 手工核（插删移动之后必跑）
```

| 脚本 | 作用 | 什么时候跑 |
|---|---|---|
| `check.sh` | 11 项校验，见下表 | 每次改完 |
| `build_book.py` | 8 节 + 前言/结语/附录拼合，镜像条自动展开 | 每次改完 |
| `build_web.py` | 生成单文件网页（零依赖，双击可开） | 每次改完 |
| `find_dupes.py` | TF-IDF 查重复条目（跨节 + 同节） | 加条、搬条、改结构之后 |
| `verify_refs.py` | 打印每处「第 N 条」实际指向哪条 | 插条、删条、移动条、换节序之后 |
| `refs.py` | 共享解析模块 + 镜像展开；被两个 build 脚本 import | 不用直接跑，可 `python3 tools/refs.py` 看镜像映射 |

### check.sh 的 11 项

```
栏位齐全          每条 5 栏（总结性建议/具体地/为什么/主观证据等级/来源）
条号连续          1..N 不得跳号
引用不越界        「第 N 条」目标必须存在
镜像引用有效      <!-- 引用：NN 节第 M 条 --> 目标必须存在
禁止引用镜像条    引用必须指向源条，不能指向镜像条
镜像条豁免栏位    镜像条正文在源条，不计入栏位数
无过期条数声明    正文不出现总数级条数（>20 的数字）
无软化词          「我觉得 / 其实 / 我建议 / 我发现」
无 AI 腔调        「不是 X，是 Y」「不是 X，而是 Y」「真正…的不是」「问题不在…在」
页脚不重复        「下一节」行不得出现多个「——」
同节无重复句      同节内 ≥14 字原句不得重复
```

## 二、镜像条：真源一处，多处显示

### 问题

同一件事在两节都该出现（例如「要不要去健身房」既属于心态，也属于花钱），但**写两份会各自漂移**——改了一处忘了另一处，读者读到两版不一致就崩了。

### 做法

正文只写一处（**源条**），另一处放标记：

```markdown
### 1. 在家练，还是去健身房？

<!-- 引用：01 节第 3 条 -->

> 本条与 01 节第 3 条「一定要去健身房吗？」是同一件事，**正文以该条为准**。
```

- `<!-- ... -->` 在 GitHub 和编辑器里不可见，但 build 脚本读得到
- 网页版 + 通读版会把**源条正文展开到这里**，并注明「正文以该条为准」
- 网页版那条提示是**可点的**，会跳到源条

### 四条规矩

1. **先合并，再引用**——对面那条里独有的内容必须先并进源条，否则一引用就丢
2. **只能用 `<!-- 引用：NN 节第 M 条 -->` 这一种写法**（check.sh 按此正则校验；节号补零写成 `01`）
3. **禁止指向镜像条**（check.sh 会报）——链条只能一层，镜像不能再引镜像
4. **别制造循环引用**（A 指 B、B 指 A）——check.sh 查不出这个，要手工看

## 三、⚠️ check.sh 查不出的那一类错

`check.sh` 能查出「引用的条号**不存在**」，但**查不出「条号存在、却不是说想那条」**。

**插条 / 删条 / 移动条 / 换节序，会让后面所有条号整体位移**，正文里所有 `见第 N 条`、`见 XX 节第 N 条` 会一起指错，而校验仍然全绿。

### 已发生过的真实案例（每一次都是靠手工核才发现）

1. 作者把「心理障碍」从 01 节第 6 条提到第 1 条、并删掉原第 1 条
   → 结语「01 节第 **13** 条」应为 **12**；该条内部「见第 **12** 条」应为 **11**。check.sh 全绿。
2. 04 节插入「管不住嘴」（成为新第 3 条）
   → 06 节「04 节第 **5** 条」应为第 **6** 条。
3. 02/03 换位 + 03 节删掉「解剖软件」条
   → 02 节「03 节第 **3** 条」应为第 **2** 条；张力条「第 **7、9** 条」应为「第 **8、10** 条」；08 节「02 节第 **14** 条」应为第 **15** 条。
4. 08 节重排时新加两条
   → 条号变成 `1,2,1,2,3,4,10,6,7,8,9`。**条号连续性校验是后来才补上的**，当时没发现。
5. README「三条线」两处都写 `06 节`（睡眠降级 / 心情不好可以练）
   → 但睡眠在恢复节（第 5 节），「心情不好可以练」早已并进 01 节第 11 条。**两处都指错**，藏了很久。

### 所以：插删移动之后必须跑

```bash
python3 tools/verify_refs.py
```

它会逐行打印「引用文字 → 实际指向的条目标题」，**用眼睛确认「→ 后面那条」是不是正文想说的那条**。当前全书 31 处引用。

## 四、结构变动规程（换节序 / 搬节 / 插条）

1. **`git mv` 改文件名**（保住历史），注意数字前缀 —— 例子：`03-训练.md` 和 `02-关键节点.md` 互换时要先移到一个临时名，避免撞名
2. 改节号：文件里的 `# N. 名称`
3. **节号引用互换用占位符两步替换**，不要直接对换（会互相覆盖）：

   ```python
   P = "\0S02\0"
   t = t.replace("02 节", P).replace("03 节", "02 节").replace(P, "03 节")
   ```

4. 改**页脚**「下一节」（顺带查有没有像 04 节那样重复印三遍的 bug）
5. 改 **README「怎么读」** 的目录 + 三条线
6. **跑 `verify_refs.py`，逐条核语义**
7. 跑上面那四个脚本

## 五、不要做的事（与作者手改的协同）

作者会自己用 VS Code 直接打开源 markdown 手改。规则：

- **不要整文件覆写** —— 只做逐句替换（`str.replace`），整文件写会冲掉他的手改
- **不要 `git add -A`** —— 只提交实际改过的文件
- **写文件前先 `git status`** —— 有他的未提交改动就先停下来确认
- **提交信息里标明「作者手改」**，以便和他的改动区分
- 怀疑他的手改被覆盖时，用 pickaxe 定位：

  ```bash
  git log -S"<他的原句>" --oneline book/
  ```

**已发生过一次**：他改的东西没进过任何一次他自己的提交，而是被后续编辑覆盖了。所以以上四条不是形式主义。

## 六、语感规则（check.sh 自动拦）

**禁用**（原话：「全文都是我的个人建议」，逐条声明是冗余）：
- 软化词：`我觉得` / `其实` / `我建议` / `我发现`
- AI 腔调对偶句：`不是 X，是 Y` / `不是 X，而是 Y` / `真正…的不是` / `问题不在…在`

**保留**（是他的语感，别误删）：
- 感叹号（情绪落点）
- 破折号（思考停顿）
- 「我猜」/「可能」——**仅限抖音口播体裁**，本指南不用

**克制**：加粗每字段至多一处；不要格言式短句收尾。

## 七、排版约定（都已被 check.sh 拦住）

### 子项一律用 `  - `，不用 `（N）` 行式枚举

```markdown
- **为什么**：
  - 健身房器械全面，性价比最高。
  - 健身房的健身人群众多，有良好的氛围。
```

`（1）` 行式在网页上会渲染成**没有项目符号的普通段落**，跟 `- ` 子项视觉不统一。
`check.sh` 现在会拦行首的 `（N）`。

顺带：行内的 `① ② ③` 可以用（它本来就是行内枚举，不占行首）。

### 多行字段必须走 `md_block`，不能用 `inline()`

`build_web.py` 里这一行踩过坑：

```python
d[f] = md_block(val) if f == "具体地" else inline(val.replace("\n", " ").strip())
```

`inline()` **会把换行压成空格**，于是「为什么」里的 `  - ` 子项被原样输出成一整段
（网页上就是一大段带着字面 `- ` 的长文本，**不换行**）。

修法：多行字段都交给 `md_block`：

```python
multi = f in ("具体地", "为什么", "总结性建议") and "\n" in val
d[f] = md_block(val) if multi else inline(val.replace("\n", " ").strip())
```

**这个坑很阴**：源 markdown 完全正确，问题在渲染层选了错的函数。
排查方法——**直接看渲染后的 DOM**：

```js
document.querySelector('#c-1-4 .v').innerHTML   // 是 <ul> 还是带字面 "- " 的 <p>？
```

### 子项缩进必须整组一致

```markdown
  - 第一条
  - 第二条      ← 不能一个 0 缩进、一个 2 缩进
```

**这个坑踩过一次**：解析时天真的 `.strip()` 会吃掉**第一个子项**的缩进，导致网页上第一个顶格、后面缩进，看起来就是「没对齐」。
`check.sh` 现在校验解析后的子项缩进一致性（查的是解析结果，不是源文本——源文本是对的）。

### 长枚举用列表，不要挤在一段里

超过 2 项的行内枚举（`① xxx ② yyy ③ zzz`）挤在一段里读起来累，拆成子项。

## 八、验证网页改动：用 DOM 量，不要截图

**作者的服务端会拒收截图**（HTTP 400 unsupported image）。所以核对网页效果一律用
`browser_console` 执行 JS 读真实渲染值，**不要用 `browser_vision` 截图**。

```js
// 例：核对左栏 + 高亮框
const s=document.querySelector('.side');
getComputedStyle(s).position            // "sticky"
document.querySelector('.layout').gridTemplateColumns   // "208px 838px"
document.querySelector('#c-1-1 .f.hl').getBoundingClientRect().width
```

好处：比看图准（能拿到 px）、省 token、不触发报错。
排查「源文件对、渲染不对」的偏差时，**看 DOM 的 innerHTML / getComputedStyle**：

```js
document.querySelector('#c-1-4 .v').innerHTML    // <ul> 还是带字面 "- " 的 <p>？
```

## 九、改 build_web.py 的两条硬规矩

**① 模板里的 JS 改完必须过 `node --check`** —— 已经内置：`build_web.py` 会抽出 `<script>` 跑语法检查，有错直接 `exit 1`。

踩过的坑：一次批量替换时把 `document.querySelectorAll("nav button")` 的尾巴接上了原句遗留的 `.forEach(`，生成出 `...forEach.forEach(...)`，**页面整块白掉**（5 个 JS 异常），而 `check.sh` 全绿——它只看 markdown。

**② 替换字符串时，尾巴不要接上原句的后半截。** 用 `str.replace(old, new)` 前先确认 `old` 覆盖了整条语句，别只替换前缀。

## 十、手写引用的条号锁定（cite-lock）

**问题**：正文里手写的「见 02 节第 15 条」，一旦在 02 节插删条目，后面的条号整体位移，
引用就静默指错——而越界校验仍然全绿（它只查条号存不存在，不查指向对不对）。
已经踩过一次：「心理障碍」提到第 1 条后，结语和条内 2 处引用错位。

**做法**：锁文件记的不是条号，是「这条引用当时指向哪一条（按标题）」。
`tools/cite-lock.json` 的键 = `源节号·源条目标题[栏位]#序号`，值 = 目标节号 + 目标标题。
**键用源条目的标题而不是条号**——源条目自己也会被重新编号，用条号当键一插删就全部失配。

```
python3 tools/citelock.py            # 只读校验（check.sh 已接入，漂移就报错）
python3 tools/citelock.py --fix      # 按标题找回当前条号，自动改源文件里的数字
python3 tools/citelock.py --update   # 把新出现的引用登记进锁文件
python3 tools/citelock.py --list     # 列出每条引用当前指向哪一条
```

**只有三种情况会出错，都要求人来定：**

| 情况 | 报错 | 处理 |
|---|---|---|
| 条号变了、标题还在 | 条号漂移 | `--fix` 自动改数字（只动数字，改完自检） |
| 标题找不到了（那条被删或改名） | 锁定目标失联 | 人工决定：改引用 / 改锁 / 恢复那条 |
| 出现没登记过的新引用 | 未登记引用 | 确认它指向哪一条，再 `--update` |

**`--fix` 写完会重新扫一遍自检**——「改是改了、改错了」这类 bug 必须当场撞出来
（开发时就撞到一次：循环变量 `ent` 串味，3 条都写成了最后一个标题）。
**`--fix` 只替换数字字符，并断言其余内容一字未动**，不会碰作者的手改。

**注意**：`--update` 是把【当前】条号登记为正确。如果引用本来就是错的（比如指向了自己），
锁定会把这个错误固化下来。**登记前跑 `--list` 把清单看一遍。**

## 十一、审核模式（作者逐条过、可直接改原文）

**网页顶栏的「审核模式」**：一次只显示一条，可以：
- **通过 / 要改** 标记（存在浏览器 localStorage，刷新不丢）
- **只看未审**：切到还没标过的
- **编辑原文**：直接改这一条的 markdown（就是 `book/*.md` 里的原文，一字不差），保存写回源文件
- **导出结果**：下载 `审核结果.md`（通过 / 要改 / 未审三组，带备注）并复制到剪贴板
- 快捷键：`←` `→` 翻条，`1` 通过，`2` 要改（在输入框里打字时不触发）

**「编辑原文」需要本地服务**（`file://` 打开的网页写不了本地文件）：

```
python3 tools/review_server.py        # 打开 http://127.0.0.1:8787/
```

写回服务只做三件事：取原文 / 写回 / 重建 + 体检。安全边界：
- 只监听 `127.0.0.1`，只有本机能连
- 只改 `book/` 下 `.md` 里「`### N. `」那一条，**其余一字不动**（尾部空白也沿用原文的，
  否则改文件里最后一条会凭空多个空行）
- **条号不能改**：新内容必须以「`### N. `」开头，否则 400 拒收
- 改完自动跑 `build_book` + `build_web` + `check.sh`，结果一并返回页面
- 源文件由 git 兜底：改坏了 `git checkout -- book/` 就回来

**注意**：保存后网页是旧的，页面会给你一个「刷新页面看结果」按钮（审核位置存在
localStorage，刷新后还停在原来那条）。

## 十二、其他注意

- **章节内引用不带节号时按本节解析**（`verify_refs.py` 已处理）
- **网上新写的条容易被 check.sh 拦**——AI 腔检查对"自己刚写的句子"命中率很高，这正常，改掉就行
- **改完记得重建**：`build_book.py` 和 `build_web.py` 都要跑，否则通读版和网页是旧的
- **`全书-通读版.md` 和 `web/` 是产物，不要手改**（会被下一次 build 覆盖）
